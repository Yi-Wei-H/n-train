# JMeter 防刷票四层防护验证

与 `order-create.jmx`（**放开**三道闸测下单产能）互补，本脚本**不开闸**，模拟机器刷票流量逐层验证闸门本身：①网关 JWT → ②用户/IP/设备指纹三维度限流 → ③图形验证码 → ④令牌大闸。全程**零订单副作用**：假乘车人被 41009 拦、令牌置 0 被 43008 拦，均发生在成单之前，不扣余票、不耗真实令牌。

## 场景与预期

| 组 | 层 | 攻击画像 | 入口 | 预期 |
|---|---|---|---|---|
| S0 准备 | - | 读账号 CSV + 连通检查 | 网关 8000 | `code=0` |
| S1A1 | L1 | 不带 token 的裸脚本 | 网关 | HTTP **401** + `40100` |
| S1A2 | L1 | 伪造乱码 token | 网关 | 401 + `40100` |
| S1A3 | L1 | 篡改 payload(sub) 不换签名 | 网关 | 401 + `40100`（验签防篡改） |
| S2a | L2-USER | 固定 userId 连发 12 次（IP/设备每次随机） | member 直连 8001 | 1~3 次 `41009` → 4~10 次 `41005` → 11 次起 `42900`「下单太频繁啦，**休息一下**」（USER 独有文案） |
| S2b | L2-IP | 随机账号 + **固定 IP** ×12 | 直连 8001 | 1~10 次 `41009`，11 次起 `42900`「请稍后重试」 |
| S2c | L2-DEVICE | 随机账号 + 随机 IP + **固定指纹** ×12 | 直连 8001 | 同上，唯一固定维度是 X-Device-Id 桶 |
| S3 | L3 | 真实账号 A 连发 5 单（假乘车人） | 网关 | 1~3 次 `41009`（频次已计数），4~5 次 `41005`（第 4 单起强制验证码，第 5 次故意填假码） |
| S4 | L4 | 账号 B 正常下单（令牌已置 0 模拟抢光） | 网关 | 200 + `43008`「当前抢票人数过多」 |
| S2d | L2 综合 | 3 账号 × 12 次并发，同出口 IP | 网关 | 全部落在 `{41005,41009,42900}`，IP 桶到 10 后整体封顶 |
| S5（默认禁用） | 全部 | 10 线程混战：奇数线程裸脚本、偶数线程持 token 高频 | 网关 | 全部 ∈ `{40100,40101,41005,41009,42900,43008}`，无 `code=0` |

**维度隔离原理**（S2a/b/c）：走网关时 `X-User-Id`/`X-Forwarded-For`/`X-Device-Id` 会被剥离重写，无法控制维度，因此直连 member 8001（本机/内网联调可达，生产不应暴露）；每请求随机化另外两个维度（18 位随机 userId、随机 IP），唯一固定的维度桶必然最先到 10 —— 第 11 次的 `42900` 只能来自该维度。S2a 顺带展示"层层剥皮"：前 3 次先被乘车人校验拦（41009），第 4 次起被验证码层拦（41005），限流是高频下的兜底。

## 准备

1. 环境起全：gateway(8000) / member(8001) / business / Redis / MySQL / Nacos。验证：

```bash
curl "http://localhost:8000/api/member/ticket/query?rideDate=2026-09-30&fromStation=AOP&toStation=CSQ"  # 应返回 code=0
```

2. 账号：准备 ≥2 个会员账号（S3/S2d 用账号 A，S4 用账号 B；第 3 行可选供 S2d 用）。各账号浏览器登录 → F12 → `localStorage['ntrain-web-token']` → 填 `anti-bot-users.csv`（每行 `token,passengerId`，B 行填 B 自己的乘车人 ID；**真实凭证，勿提交 git**）。
3. S4 前把车次令牌置 0（模拟令牌已被抢光；key 按 rideDate/trainCode 拼）：

```bash
redis-cli -h <REDIS_HOST> [-a <pwd>] SET "ntrain:sk:token:2026-09-30:D901" "0"
```

4. 重复运行注意：限流桶 60s 滑窗自动过期；验证码标记 TTL 10 分钟（`redis-cli DEL "ntrain:order:captcha:required:<memberId>"` 可手动清）；连跑请间隔 60s 以上或换账号行。

## 运行

```bash
jmeter -n -t doc/jmeter/anti-bot.jmx -Jhost=localhost -l anti-bot.jtl -e -o anti-bot-report
# 覆盖业务参数：-JrideDate=2026-09-30 -Jtrain=D901 -Jfrom=AOP -Jto=CSQ -Jseat=5
# 直连端口非默认时：-Jmport=8001；网关非默认：-Jgport=8000
```

## 读数

- **断言失败数 = 0 且 Error% ≈ 0 → 四层全部按预期拦截**（脚本对 401 已改标成功，Error%/断言失败只反映真实漏拦）。
- 任何场景出现 `code=0` = 对应层被穿透（S4 成单说明令牌未置 0 或已懒重建）。
- 断言失败信息内置了排查提示（token 失效 / 限流桶污染 / 标记残留 / 令牌未置 0），按提示处理后重跑对应线程组即可。
- HTML 报告按 label 分组看各场景响应分布；S2a 的"1~3 次 41009 → 4~10 次 41005 → 42900"梯度即第三层触发、第二层兜底的直观证据。

## 恢复

```bash
redis-cli -h <REDIS_HOST> [-a <pwd>] DEL "ntrain:sk:token:2026-09-30:D901"   # 下次下单按 DB b_sk_token.remaining 懒重建
```

无订单与库存副作用，无需清理订单。

## 局限（对抗升级方向）

- 同机压测出口 IP 唯一：S2d 的 IP 桶即压测机 IP；生产多 IP 刷票需 JMeter 分布式多机发压验证。
- XFF 伪造仅在直连 8001 时生效（网关剥离重写）；这正是维度隔离场景走直连的原因，8001 不应对公网暴露。
- 设备指纹维度可被随机 `X-Device-Id` 绕开（S2/S3 每请求随机指纹即模拟此攻击）；开源版 FingerprintJS 的定位是抬高脚本门槛 + 解决 NAT 误伤，强对抗需 FingerprintJS Pro 服务端识别或风控平台。
- 验证码层演示的是"缺码/错码被拒"（41005）；打码平台 OCR 破解场景未覆盖。
